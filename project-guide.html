1 Project Overview
▾

DOT-LOGGER is a full-stack AI chatbot web application — a personal ChatGPT clone. Authenticated users can have multi-turn conversations with an LLM. Every message is persisted to MongoDB so conversations survive page refreshes and sessions. The AI backend was originally OpenAI GPT-3.5, later migrated to Groq (LLaMA 3.1) for free-tier access.

Architecture Decisions — and Why

Why MERN?

JavaScript (TypeScript) runs on both the client and server. One language across the full stack reduces context switching — the same destructuring, async/await, and array methods work in both places. MongoDB's flexible document model also pairs naturally with JavaScript objects, avoiding the impedance mismatch you'd get with an ORM over a relational DB.

Why store chats inside the User document? (Embedded / Denormalized)

Design Decision
Chats are stored as a subdocument array inside the User document, not in a separate chats collection. This means one MongoDB query fetches both the user and all their chat history at once — no JOIN or secondary query needed. The trade-off is acceptable here because one user's chats are never queried independently of their owner; they always travel together.

Why JWT + HTTP-only signed cookies instead of localStorage?

  • HTTP-only: The cookie cannot be read by JavaScript — protects against XSS attacks that would steal a token from localStorage.
  • Signed cookies: The backend signs the cookie with COOKIE_SECRET. Any tampering invalidates the signature — the server rejects it before even decoding the JWT.
  • JWT (stateless): The server doesn't store session data. The token itself carries the user's ID and email, verified by signature. No DB lookup needed to validate a session — only for protected data.

Why Context API instead of Redux?

The app has exactly one piece of global state: is the user logged in, and who are they? Redux introduces boilerplate (actions, reducers, store) that is disproportionate for this use case. Context API with a single AuthProvider is sufficient and keeps the bundle small.

Why Vite + SWC instead of Create React App?

CRA uses Webpack which bundles the entire app before serving. Vite uses native ES modules — it serves files on-demand in development, making hot reload near-instant. SWC (Speedy Web Compiler, written in Rust) replaces Babel for TypeScript/JSX compilation and is 20–70× faster.

Why TypeScript on both sides?

The frontend calls the backend API and expects specific response shapes. With TypeScript on both sides you can define shared types and catch mismatches at compile time. For example, if the backend changes a response field name, the TypeScript compiler will flag all frontend call-sites that relied on the old name.

Key Separation of Concerns

  • routes/ — only define URL paths and their middleware chains. No business logic.
  • controllers/ — contain all business logic. They read from the request, talk to the DB/AI, and write to the response.
  • utils/ — pure utilities that are reusable across controllers (token creation, validation, constants).
  • config/ — third-party client instantiation (Groq SDK). Keeps API setup separate from usage.
  • context/ vs helpers/ — context owns state and state transitions; helpers are just thin wrappers around axios HTTP calls.

import mongoose from "mongoose";
import { randomUUID } from "crypto";

// ── Subdocument schema for a single chat message ──
const chat = new mongoose.Schema({
    id: {
        type: String,
        default: randomUUID(),   // ⚠️ called once at module load, not per document
    },
    role: {
        type: String,
        required: true           // "user" or "assistant"
    },
    content: {
        type: String,
        required: true
    }
})

// ── Top-level User document schema ──
const user = new mongoose.Schema({
    name:     { type: String,  required: true },
    email:    { type: String,  required: true,  unique: true },
    password: { type: String,  required: true }, // bcrypt hash, never plaintext
    chats:    [chat]                              // embedded array of chat subdocs
})

export default mongoose.model('User', user)

Embedded vs Referenced — the Design Choice

Why chats are embedded inside the User document
  • Single query: When you load a user's chat page you only need User.findById(id) — you get the user and all their chats in one round-trip to MongoDB.
  • No cross-collection relationships: Chats only ever belong to one user and are never queried independently, so there's no benefit to a separate collection.
  • Trade-off: If a user has thousands of messages, the document grows large. A separate chats collection with a userId reference would scale better for power users.
Known Bug: randomUUID() called once
default: randomUUID() is evaluated once when the module loads, not each time a new chat subdocument is created. Every chat message in the DB ends up with the same id. The fix is default: randomUUID (passing the function reference, not calling it).

validate(validations) — utils/validators.ts

A higher-order function — it takes an array of validator chains and returns a new middleware function. This is the factory/middleware-factory pattern.

backend/src/utils/validators.ts 
const validate = (validations: ValidationChain[]) => {
    // Returns a new middleware function:
    return async (req: Request, res: Response, next: NextFunction) => {
        for (let validation of validations) {
            const result = await validation.run(req)
            if (!result.isEmpty()) {
                break   // early exit on first error
            }
        }
        const errors = validationResult(req)
        if (errors.isEmpty()) {
            return next()   // all good — proceed to next middleware
        }
        return res.status(422).json({ errors: errors.array() })
    }
}

Concepts: Higher-order function async/await for...of loop Express middleware signature TypeScript generics

createToken(id, email, expiresIn) — utils/token_manager.ts

Creates a signed JWT token. The payload is the minimal user identity needed on the server side. The token is signed with JWT_SECRET — only the server can create or verify it.

backend/src/utils/token_manager.ts 
export const createToken = (id: string, email: string, expiresIn: string) => {
    const payload = { id, email }   // object shorthand: {id: id, email: email}
    const token = jwt.sign(payload, process.env.JWT_SECRET, { expiresIn })
    return token
}

Concepts: Object literal shorthand JWT signing TypeScript parameter types

verifyToken — utils/token_manager.ts

Express middleware that authenticates every protected route. It wraps the callback-based jwt.verify() in a Promise — this is the Promise constructor pattern for converting older callback APIs to async/await compatible code.

backend/src/utils/token_manager.ts 
export const verifyToken = async (req: Request, res: Response, next: NextFunction) => {
    const token = req.signedCookies[`${COOKIE_NAME}`]
    if (!token || token.trim === ("")) {   // ⚠️ bug: trim is a function, not a value
        return res.status(401).json({ message: "token not recieved" })
    }
    return new Promise<void>((resolve, reject) => {
        return jwt.verify(token, process.env.JWT_SECRET, (err, success) => {
            if (err) {
                reject(err.message)
                return res.status(401).json({ message: "token expired!" })
            } else {
                console.log('verification successfull')
                resolve()
                res.locals.jwtData = success   // decoded payload available to controllers
                return next()
            }
        })
    })
}

Concepts: Promise wrapping callback res.locals pattern TypeScript generics Promise<void> Signed cookies

generateResponse — chat_controllers.ts

The core chat handler. Sends the entire conversation history to the AI on every message — this is how multi-turn conversation context is maintained (the LLM has no memory, so you must re-send all previous messages each time).

backend/src/controlllers/chat_controllers.ts 
export const generateResponse = async (req: Request, res: Response, next: NextFunction) => {
    const { message } = req.body                    // destructuring
    const userID = await User.findById(res.locals.jwtData.id)

    if (!userID) return res.status(400).json({ msg: 'user not found!' })

    // Map to {role, content} shape expected by Groq API
    const chats = userID.chats.map(({ role, content }) => {
        return ({ role, content })
    }) as { role: "user" | "assistant", content: string }[]  // type casting

    chats.push({ role: "user", content: message })     // add new message to context
    userID.chats.push({ role: "user", content: message })

    await userID.save()                               // ← save user message FIRST

    const groq = configGroq()
    const chatResponse = await groq.chat.completions.create({
        model: "llama-3.1-8b-instant",
        messages: chats,    // full history gives the LLM conversation context
    })

    userID.chats.push(chatResponse.choices[0].message)  // add AI response
    await userID.save()                               // ← save AI response
    return res.status(200).json({ chats: userID.chats })
}

Concepts: Array.map() Destructuring Type casting (as) Dual-save strategy LLM context management

AuthProvider — context/AuthContext.tsx

Provides the global auth state tree to the entire React component tree. The useEffect with an empty dependency array [] means "run once on mount" — it checks if there's already a valid session cookie when the page loads.

vite-project-frontend/src/context/AuthContext.tsx 
export const AuthProvider = ({ children }: { children: ReactNode }) => {
    const [user, setUser] = useState<User | null>(null)
    const [isLoggedIn, setIsLoggedIn] = useState(false)

    useEffect(() => {
        const checkStatus = async () => {       // inner async function (useEffect can't be async)
            const data = await checkAuthUser()
            if (data) {
                setUser({ email: data.email, name: data.name })
                setIsLoggedIn(true)
            }
        }
        checkStatus()
    }, [])  // empty array = run once on mount

    const login = async (email: string, password: string) => {
        const data = await logInUser(email, password)
        if (data) {
            setUser({ name: data.name, email: data.email })
            setIsLoggedIn(true)
        }
    }
    // ... signup, logout ...
    const value = { user, isLoggedIn, login, signup, logout }
    return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>
}

export const useAuth = () => useContext(AuthContext)  // custom hook

handleSubmit in Chat.tsx

Sends a chat message. Uses an uncontrolled input (ref) instead of state for the text field — this avoids a re-render on every keystroke. The optimistic update adds the user message to the UI immediately before the API responds, making the app feel instant.

vite-project-frontend/src/pages/Chat.tsx 
const handleSubmit = async () => {
    const content = inputRef.current?.value as string    // read from DOM via ref
    if (inputRef && inputRef.current) {
        inputRef.current.value = ""                      // clear input directly (no state)
    }
    const newMessage: message = { role: 'user', content }
    setChatHistory((prev) => {
        return ([...prev, newMessage])                   // optimistic update (spread)
    })
    const chatData = await sendChatReq(content)
    setChatHistory([...chatData.chats])                  // replace with DB truth
}

State Management — Context API

The app has one piece of global state: authentication. It is managed in AuthContext.tsx and made available app-wide through React Context. Any component that needs to know if the user is logged in (or who they are) calls useAuth().

Context vs Props Drilling
Without Context, isLoggedIn would need to be passed as props from App → Header → Navlink, and also down to Chat, Home, etc. Context eliminates this "prop drilling" by making state globally accessible.

useRef vs useState — Chat Input

useStateuseRef (used here)
Re-renders on change?Yes, on every keystrokeNo
Value accessvalue state variableinputRef.current.value
ClearingsetValue("")inputRef.current.value = ""
Use caseForm fields that need validation on changeSubmit-only inputs (read once on submit)

For the chat input, the value is only needed when the user clicks send. Reading it via ref avoids unnecessary re-renders on every keystroke, improving performance.

Optimistic Update Pattern

When the user sends a message, the chat item appears in the UI immediately — before the API call completes. This is an optimistic update:

  1. Add user message to local state → UI re-renders instantly
  2. Send API request (takes ~500–2000ms)
  3. When API responds, replace the entire chatHistory with the server's version

This makes the app feel responsive. If the API fails, the optimistic update remains visible but the AI response never appears — ideally you'd roll back on error, but this isn't implemented here.

9 Interview Prep
▾

Likely questions from a senior interviewer about this specific project, with answers grounded in the actual code.

1. Why did you store chats inside the User document instead of a separate collection? +

Chats in this app are always accessed alongside their owner — you never need to query all chat messages across users, or find a chat by its own ID independently. Embedding them in the User document means a single User.findById() call retrieves both the user profile and their full conversation history in one round-trip.

The trade-off is document size. MongoDB has a 16MB document limit, and a very active user could accumulate thousands of messages. For this scale of project it's acceptable. At production scale I'd move to a separate chats collection with a userId reference, and paginate the chat history.

2. How does your authentication work end-to-end? +

When a user logs in, the backend verifies their credentials, then creates a JWT token containing their user ID and email, signed with a secret only the server knows. This token is sent to the browser as a signed, HTTP-only cookie.

On every subsequent request to a protected route, the browser automatically includes this cookie. The verifyToken middleware reads the signed cookie (the signing prevents client-side tampering), verifies the JWT signature, decodes the payload, and stores it in res.locals.jwtData. Controllers downstream then use res.locals.jwtData.id to identify the user.

The auth is stateless — the server doesn't store session data. The token itself carries everything needed for verification.

3. What is the purpose of signing the cookie, and why use HTTP-only? +

Signed cookies: When cookieParser(COOKIE_SECRET) signs a cookie, it appends an HMAC signature to the cookie value. If the client modifies the cookie value at all, the signature no longer matches and the server rejects it as invalid. This prevents cookie tampering.

HTTP-only: The cookie cannot be accessed by JavaScript running in the browser — document.cookie won't show it. This protects against XSS (Cross-Site Scripting) attacks. If an attacker injects malicious JS into your page, they cannot steal the auth token because JS literally cannot read HTTP-only cookies.

Together, these two properties make cookie-based auth significantly more secure than storing a JWT in localStorage, which can be read by any JS on the page.

4. Explain the middleware chain for a protected chat route. +

For POST /api/v1/chat/new, three middleware functions run in sequence before the controller:

  1. validate(chatValidator) — checks that req.body.message is not empty. If it is, returns 422 immediately. This is a higher-order function — validate() takes the validator array and returns the actual middleware function.
  2. verifyToken — reads the signed auth_token cookie, verifies the JWT signature, and if valid, stores the decoded payload ({id, email}) in res.locals.jwtData. Returns 401 if missing or expired.
  3. generateResponse — the actual controller. By this point, we know the message is valid and the user is authenticated. It uses res.locals.jwtData.id to find the user in MongoDB.

Each step is a gate — if it fails, the request stops there and doesn't proceed to the next step.

5. Why is validate() considered a higher-order function? +

A higher-order function either takes a function as an argument or returns a function (or both). validate() does both:

  • It takes validations: ValidationChain[] — an array of validator functions
  • It returns a new async (req, res, next) => {...} function — which is the actual Express middleware

This pattern is called a middleware factory. It lets you create parameterized middleware — the same validate() function produces different validators depending on what array you pass in: validate(signupValidator), validate(loginValidator), etc.

6. What is the difference between controlled and uncontrolled inputs? Which did you use in the chat input and why? +

Controlled input: The value is driven by React state. Every keystroke calls onChange → setState → re-render. The input's value is always in sync with the state variable.

Uncontrolled input: The value lives in the DOM. React doesn't manage it. You read it via a ref only when you need it (e.g., on submit).

In Chat.tsx, I used an uncontrolled input with a ref. The chat input's value is only needed when the user clicks send — there's no need to validate on every keystroke or show a character count. Using a ref avoids re-rendering the entire chat component on every keystroke, which would be wasteful given the chat history is rendered in the same component.

7. What does withCredentials: true do in your axios config? +

By default, browsers do not include cookies in cross-origin requests. Since the frontend (port 5173) is making requests to the backend (port 5000), these are technically cross-origin requests.

Setting axios.defaults.withCredentials = true tells the browser to include the auth_token cookie on every axios request, even though it's cross-origin. Without this, the backend's verifyToken middleware would never receive the cookie, and all protected routes would return 401.

This only works because the backend CORS is also configured to allow credentials: cors({ origin: "http://localhost:5173", credentials: true }). Both sides must opt in.

8. What is the Context API and why did you choose it over Redux? +

React Context API is a built-in mechanism to share state across the component tree without passing props manually at every level. You create a context, wrap your app in a Provider, and any component can subscribe to that context with useContext().

Redux is a more powerful state management library — it adds a global store, action creators, reducers, and middleware. It's well-suited for complex apps where state changes are frequent, involve many components, or need time-travel debugging.

For DOT-LOGGER, the only global state is authentication — a single object with isLoggedIn, user, and three functions. That doesn't justify the boilerplate of Redux. Context API achieves the same result with just one file (AuthContext.tsx) and no extra dependencies.

9. How does your app persist chat history across page refreshes? +

Two separate persistence mechanisms work together:

  1. Session persistence: When the page loads, AuthProvider's useEffect calls checkAuthUser() → hits GET /user/auth-status. The browser sends the auth_token cookie automatically. If the token is still valid, the user is restored to the logged-in state without entering their password again.
  2. Chat history persistence: When Chat.tsx mounts, its useEffect calls getChatsReq() → hits GET /chat/new. The backend finds the user by their JWT ID and returns their full chats array from MongoDB. The component's chatHistory state is populated from this response.

Every message is saved to MongoDB immediately when sent (before even calling the AI), ensuring nothing is lost even if the AI API fails.
